# ResInvest ERP Serwer — baza PostgreSQL (tryb firmowy, od 3.15)

Od wersji 3.15 tryb firmowy pracuje na **PostgreSQL**. Przejście wykonuje instalator (rozdz. 2): przy aktualizacji
przenosi dane z SQLite do PostgreSQL z kontrolą zgodności i przełącza serwer. Serwer obsługuje dwa silniki bazy:

| Tryb | Ustawienie | Zastosowanie |
|---|---|---|
| **PostgreSQL** | `DB_DRIVER=postgres` | praca firmowa: centralna baza, wielu użytkowników, kopie i odtwarzanie także narzędziami PostgreSQL |
| **SQLite** | `DB_DRIVER=sqlite` (domyślnie) | jedno stanowisko, tryb awaryjny, punkt powrotu po wycofaniu migracji |

Tryb OFFLINE programu (plik `ResInvest_ERP.html` otwarty bez serwera) nie używa żadnej z tych baz —
dane trzyma przeglądarka. Nic się w nim nie zmienia.

Silnik aplikacji (`app/src/engine.js`, `service.js`), interfejs, API (`/api/*`), uprawnienia, numeracja dokumentów,
korekty, inwentaryzacja, raporty i poczta są **te same** w obu trybach. Zmieniona jest wyłącznie warstwa zapisu.

## 1. Architektura

```
przeglądarki ──HTTP──▶ riw-server.mjs ──▶ Store (core.mjs) ──▶ server/db
                         (API, sesje)      stan w pamięci,         ├─ sqlite.mjs    node:sqlite (plik lokalny)
                                           transakcja na komendę   └─ postgres.mjs  ─▶ pg-worker.mjs ─▶ PostgreSQL
```

* `server/db/schema.mjs` — jedno źródło schematu dla obu silników (9 tabel: `meta`, `state`, `rows`, `journal`,
  `accounts`, `sessions`, `login_log`, `tokens`, `outbox`) i opis kolumn używany przy przenoszeniu danych.
* `server/db/sqlite.mjs` — dotychczasowy sterownik bez zmian zachowania (WAL, `synchronous=FULL`, `VACUUM INTO`).
* `server/db/postgres.mjs` — ten sam interfejs (`exec` / `prepare` → `get` / `all` / `run` / `iterate`), tłumaczenie
  poleceń na dialekt PostgreSQL, wywołania synchroniczne przez wątek roboczy (`pg-worker.mjs`, sterownik `pg`).
* `server/db/transfer.mjs` — import SQLite → PostgreSQL, eksport PostgreSQL → plik `.sqlite`, odciski tabel.
* `server/migrate.mjs`, `tools/db-migrate.mjs` — migracja, kontrola, wycofanie, przywracanie.

### Odwzorowanie danych (1:1)

| SQLite | PostgreSQL | Dlaczego |
|---|---|---|
| `TEXT` | `TEXT COLLATE "C"` | porównanie bajtowe jak w SQLite; znaczniki czasu to tekst ISO-8601 (UTC) wchodzący do skrótów dziennika |
| `json TEXT` | `TEXT` (nie JSONB) | sumy SHA-256 liczone z dokładnego tekstu JSON |
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | identyfikatory zachowane, numeracja kontynuowana |
| `REAL` | `DOUBLE PRECISION` | ta sama reprezentacja liczb — kolejność rekordów bez zmian |
| wyzwalacze `journal_no_update/delete` | wyzwalacze + blokada `TRUNCATE` | dziennik zmian tylko do dopisywania |

### Wielu użytkowników, transakcje, ochrona danych

* **Jedna komenda = jedna transakcja**: zmienione rekordy, rdzeń stanu i wpis dziennika zapisują się razem albo wcale.
* **Jeden serwer zapisujący na bazę** — blokada doradcza PostgreSQL. Druga instancja serwera na tej samej bazie
  nie startuje (komunikat wskazuje, kto trzyma blokadę). Wielu użytkowników obsługuje jeden serwer, który
  ustawia komendy w kolejce — tak jak dotychczas.
* **Kontrola rewizji przy każdym zapisie** (`SELECT … FOR UPDATE`): jeżeli dane zmienił inny proces, zapis jest
  odrzucany w całości, a serwer wczytuje stan z bazy przed następną operacją.
* **Zerwane połączenie** (restart bazy, sieć): poza transakcją — ponowne połączenie i ponowienie; w transakcji —
  baza wycofuje zmiany. Gdy połączenie zginęło w chwili zatwierdzania, serwer sprawdza w dzienniku, czy zapis
  się dokonał. Jeżeli nie da się tego sprawdzić, użytkownik dostaje komunikat „sprawdź, czy operacja została
  zapisana”, a serwer wczytuje stan z bazy przed kolejną operacją — nigdy nie pracuje na stanie innym niż zapisany.
* **Spójność**: sumy SHA-256 każdego rekordu i łańcuch skrótów dziennika działają identycznie (`--check`).

## 2. Wdrożenie: instalacja / aktualizacja do 3.15 (migracja produkcyjna)

To jest zalecana droga — migrację produkcyjną wykonuje instalator na serwerze firmy.

1. **PostgreSQL 14+** zainstalowany na serwerze firmy albo na innym komputerze w sieci (instalator EDB dla Windows;
   zalecany 16 lub 17). Zapamiętaj hasło konta `postgres` ustawione podczas jego instalacji.
2. Uruchom `ResInvestERP_SerwerFirma.exe` (3.15). Instalator zatrzymuje serwer i robi kopię bazy (jak dotychczas).
3. Strona **„Baza danych PostgreSQL”**:

   | Pole | Wartość |
   |---|---|
   | Serwer PostgreSQL | `127.0.0.1` (ten komputer) albo adres / nazwa serwera bazy |
   | Port | `5432` |
   | Nazwa bazy programu | `resinvest` |
   | Konto programu | `resinvest_app` — zwykłe konto, bez uprawnień administratora |
   | Hasło konta programu | puste = instalator wygeneruje silne hasło i zapisze je tylko w `server.env` |
   | Administrator PostgreSQL / hasło | `postgres` i jego hasło — używane jednorazowo do utworzenia konta i bazy, **nie jest zapisywane** |

   Bez hasła administratora: konto i baza muszą już istnieć (rozdz. 3), wpisz wtedy hasło konta programu.
   Pole „Bez PostgreSQL — pozostań na SQLite” zostawia serwer na pliku SQLite (jedno stanowisko / tryb awaryjny).
4. Po skopiowaniu plików instalator wykonuje (`riw-server.mjs --db-setup`):
   * utworzenie konta i bazy programu (gdy ich nie ma), próbę połączenia, zapis danych połączenia do `server.env`,
   * **przeniesienie danych** z `resinvest.sqlite`: jedna transakcja, porównanie każdej tabeli (liczba wierszy, SHA-256)
     przed zatwierdzeniem, kontrola rdzeniem serwera (rewizja, stan, łańcuch dziennika), raport w `…\migracja\`,
   * kopię `resinvest-…-przed-aktualizacja-3_14_0.sqlite` w `backups` (pierwsze otwarcie bazy przez 3.15),
   * przełączenie serwera: `DB_DRIVER=postgres` — **dopiero po udanej migracji**.
   Wynik pokazuje okno z liczbą wierszy, rewizją, liczbą operacji i ścieżką raportu.
5. Gdy cokolwiek się nie uda (złe hasło, brak połączenia, niezgodność danych), okno pokazuje przyczynę, a serwer
   **zostaje na SQLite** — dane są bezpieczne, program działa. Ponowne uruchomienie instalatora pokaże stronę znowu.
   Jeżeli wskazana baza PostgreSQL zawiera *inne* dane, nic nie jest nadpisywane (decyzja administratora, rozdz. 3).
6. Plik `resinvest.sqlite` zostaje **bez zmian** jako punkt powrotu (rozdz. 5). Kolejne aktualizacje nie pokazują
   strony „Baza danych” — serwer pracuje już na PostgreSQL, kopia przed aktualizacją powstaje z PostgreSQL.

Przeniesienie danych z **innego systemu** (nie z SQLite programu): po instalacji administrator wpisuje stany magazynów
RiC Zabrze, RiC Brąszewice i RiC Rokitki w **Kartoteki → Stany początkowe** (dokument „Bilans otwarcia”).

Instalacja cicha (`/VERYSILENT`) pomija stronę „Baza danych” i nie zmienia silnika bazy.
Baza na innym komputerze: w `pg_hba.conf` dopuść tylko adres serwera ERP (`hostssl resinvest resinvest_app <adres>/32
scram-sha-256`), włącz `ssl = on` i ustaw w `server.env` `DB_SSL=verify-full` (albo co najmniej `require`).

## 3. Migracja ręczna (narzędzie `ResInvestERP-Migracja.cmd`)

Do sytuacji nietypowych: konto i baza zakładane przez administratora bazy, przeniesienie na inny serwer, powtórka.
Konto i baza (psql lub pgAdmin, jako `postgres`):

```sql
CREATE ROLE resinvest_app LOGIN PASSWORD '<silne hasło>' NOSUPERUSER NOCREATEDB NOCREATEROLE;
CREATE DATABASE resinvest OWNER resinvest_app ENCODING 'UTF8' TEMPLATE template0;
```

Dane połączenia w `C:\ProgramData\ResInvestERP\server.env` (`DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`,
`DB_DRIVER=sqlite` do czasu przełączenia). **Serwer zatrzymany.**

| Krok | Polecenie | Co robi |
|---|---|---|
| 3.1 | `ResInvestERP-Kopia.cmd` | kopia zapasowa przed zmianą |
| 3.2 | `ResInvestERP-Migracja.cmd plan` | **tylko odczyt**: kontrola źródła, liczby rekordów, stan bazy docelowej |
| 3.3 | `ResInvestERP-Migracja.cmd migrate --confirm` | import w jednej transakcji z porównaniem każdej tabeli przed zatwierdzeniem; raport `…\migracja\raport-migracji-*.json` |
| 3.4 | w `server.env`: `DB_DRIVER=postgres` | przełączenie serwera |
| 3.5 | `ResInvestERP-Serwer.cmd`, potem `ResInvestERP-Kontrola.cmd` | start na PostgreSQL, kontrola spójności |

`migrate` odmawia, gdy baza docelowa zawiera dane; `--replace` zastępuje je, zapisując wcześniej ich kopię
(`…-pre-migracja.sqlite`). `verify` porównuje plik SQLite z PostgreSQL tabela po tabeli.
Kody wyjścia: 0 — powodzenie, 1 — błąd lub niezgodność (baza docelowa bez zmian), 2 — błędne wywołanie.

## 4. Kopie zapasowe i przywracanie

* Kopie działają **tak samo jak dotychczas**: automatycznie raz dziennie i przy starcie, ręcznie z programu
  (przycisk kopii zapasowej) i `ResInvestERP-Kopia.cmd`, z drugą kopią w folderze firmy (`BACKUP_COPY_TO`).
* W trybie PostgreSQL kopia to **spójny obraz bazy** (transakcja `REPEATABLE READ`) zapisany jako plik
  `resinvest-<data>-<powód>.sqlite` **w formacie serwera**. Jeden format = jedna procedura przywracania i wycofania,
  niezależna od wersji PostgreSQL i bez zewnętrznych programów.
* Przywracanie (serwer zatrzymany): `runtime\node.exe server\riw-server.mjs --restore <plik.sqlite>`
  — plik jest sprawdzany (spójność, sumy kontrolne, dziennik), bieżąca baza zapisywana jako `…-pre-restore.sqlite`,
  dane zastępowane w jednej transakcji, a wynik ponownie sprawdzany. Plik niebędący kopią jest odrzucany.
* Zalecane dodatkowo (poza programem): `pg_dump -Fc resinvest` w harmonogramie zadań i/lub archiwizacja WAL
  (odtwarzanie do dowolnej chwili) oraz kopia całego serwera.

---

## 5. Wycofanie migracji

**A. Zaraz po migracji, bez pracy na PostgreSQL** — w `server.env` ustaw `DB_DRIVER=sqlite`. Oryginalny plik
`resinvest.sqlite` jest nietknięty; serwer startuje jak przed migracją.

**B. Po okresie pracy na PostgreSQL** (dane wprowadzone w PostgreSQL mają zostać):

1. zatrzymaj serwer,
2. `ResInvestERP-Migracja.cmd rollback` — zapisuje bazę PostgreSQL do `backups\resinvest-<data>-rollback.sqlite`
   i sprawdza zgodność pliku z bazą (tabela po tabeli) oraz spójność rdzeniem serwera,
3. w `server.env`: `DB_DRIVER=sqlite`,
4. `runtime\node.exe server\riw-server.mjs --restore "<plik rollback>"` — dotychczasowy `resinvest.sqlite`
   zostaje jako `…-pre-restore.sqlite`,
5. uruchom serwer, wykonaj `ResInvestERP-Kontrola.cmd`.

Baza PostgreSQL nie jest przy tym zmieniana ani usuwana.

## 6. Duża baza (lata pracy, skany)

Zmierzone na bazie z 15 000 operacji (w narzędziu obciążeniowym projektu ≈ 10 lat pracy):

| Pomiar | SQLite | PostgreSQL |
|---|---|---|
| Rozmiar bazy | 91 MB | 53 MB |
| Wczytanie stanu i kontrola spójności (start serwera) | 1,9 s | 2,1 s |
| Migracja SQLite → PostgreSQL z kontrolą (45 207 wierszy) | — | 15 s |
| Kopia zapasowa | — | 3,5 s |
| 40 stanowisk otwiera program jednocześnie (pełny stan, gzip 2,9 MB / 73 MB JSON) | — | 3,1 s wszystkie, pamięć serwera ok. 580 MB |

* **Skany dokumentów i zdjęcia** są plikami w `<dane>\skany` (jak dotychczas), nie w bazie — baza nie rośnie od skanów.
  Kopie skanów: `backups\skany` i folder firmy.
* Silnik programu (bez zmian) trzyma w pamięci serwera cały stan i przy otwarciu programu wysyła stanowisku jego pełny
  widok; dalsza praca to same zmiany. Przy wielokrotnie większej historii warto zaplanować archiwizację lat zamkniętych —
  to zmiana silnika, poza zakresem przejścia na PostgreSQL.
* Kopia zapasowa z PostgreSQL wstrzymuje serwer na czas eksportu (3,5 s przy 15 000 operacji); kopia automatyczna
  działa o 2:00. Dodatkowo zalecany `pg_dump -Fc resinvest` w Harmonogramie zadań.

## 7. Bezpieczeństwo

* Hasło bazy tylko w `server.env` (ProgramData) lub w zmiennych środowiskowych; nie jest wypisywane w dzienniku,
  w komunikatach błędów ani wysyłane do przeglądarki.
* Wszystkie wartości trafiają do bazy jako parametry wiązane — tekst wpisany przez użytkownika nie jest
  doklejany do poleceń SQL.
* Konto bazy bez uprawnień administratora; osobna baza; połączenie szyfrowane poza jednym komputerem.
* Hasła użytkowników: scrypt; sesje i tokeny: w bazie tylko skróty SHA-256 — bez zmian.
* Dziennik zmian tylko do dopisywania (wyzwalacze) + łańcuch skrótów wykrywający ręczną ingerencję.

## 8. Eksploatacja

| Sytuacja | Zachowanie |
|---|---|
| PostgreSQL niedostępny przy starcie | serwer nie startuje (kod 3), komunikat w dzienniku |
| Restart PostgreSQL w trakcie pracy | serwer łączy się ponownie (do `DB_RECONNECT_SECONDS`), praca trwa |
| Baza niedostępna dłużej | operacje kończą się błędem bez zapisu; po powrocie bazy praca trwa bez restartu serwera |
| Drugi serwer ERP na tej samej bazie | nie startuje (kod 2) |
| Aktualizacja programu | przed zmianą danych powstaje kopia `…-przed-aktualizacja-<wersja>.sqlite` (jak dotychczas) |

Ustawienia: `DB_STATEMENT_TIMEOUT_MS` (60000), `DB_CONNECT_TIMEOUT_MS` (15000), `DB_RECONNECT_SECONDS` (20),
`DB_SCHEMA` (puste = `public`), `DB_SSL`, `DB_SSL_CA`.

## 9. Testy

```
set RIW_TEST_PG_URL=postgres://postgres:<hasło>@127.0.0.1:5432/postgres
npm run test:pg
```

Testy tworzą i usuwają własne bazy `riw_t_*` na wskazanym klastrze **testowym** (rola `riw_test_app` bez uprawnień
administratora). Bez `RIW_TEST_PG_URL` testy PostgreSQL są pomijane. Zakres i wyniki: `docs/RAPORT_MIGRACJI_POSTGRESQL.md`.
Pomiar wydajności: `npm run db:bench -- <katalog> <sqlite|postgres> [adres pustej bazy] [liczba operacji]`.
